# ヘッドレスフォームについて – 概念とFAQ {#understanding-headless-forms}

このガイドでは、ヘッドレスフォーム全般に関するよくある質問と、AEM ヘッドレスアダプティブFormsに適用されるヘッドレスフォームに関する一般的な質問について説明します。 ヘッドレスアプローチを採用するタイミングや、スタックにフォームを実装、スタイル設定、統合する方法を決定するのに使用します。

## 基本と理解 {#basics-understanding}

### ヘッドレスフォームライブラリとは何ですか？

**ヘッドレスフォームライブラリ**&#x200B;は、**フォームロジック** （状態、検証、ルール、送信）を&#x200B;**プレゼンテーション** （UI コンポーネントとスタイル設定）から分離するフォームソリューションです。 「head」は表示可能なフォーム UIです。「headless」とは、ライブラリが固定UIを指示したり出荷したりしないことを意味します。 むしろ、次の項目を明らかにしています。

* **フォームモデル** （多くの場合JSON）：構造、フィールド、制約、ルール。
* フォームの状態の読み取りと更新、検証の実行、送信の処理を行うための&#x200B;**APIまたはフック**&#x200B;です。
* **イベントとライフサイクル**&#x200B;を使用して、UIが変更に対応できるようにします。

AEM ヘッドレスアダプティブFormsでは、フォームはAdobe Experience Managerでホストされている[JSON構造](architecture.md)です。 [Forms Web SDK](architecture.md#developer-tools) （クライアントサイドランタイム）は、ロジックレイヤー（ビジネスルールプロセッサー、ステート管理、検証）を提供しますが、アプリはその構造をレンダリングするUIを提供します。

### ヘッドレスフォームと従来のフォームライブラリの違い？

| 項目 | 従来のフォームライブラリ | ヘッドレスフォームライブラリ |
|--------|---------------------------|------------------------|
| **UI** | 組み込みのコンポーネントとスタイルを備えた出荷 | UIは用意されていませんが、独自のコンポーネントを使用できます |
| **スタイル設定** | ライブラリコンポーネントのテーマ設定または上書き | フルコントロール：デザインシステムをそのまま使用 |
| **フォーム定義** | 多くの場合、コードのみ（JSX/HTMLのコンポーネント） | 多くの場合、データドリブン型（JSON/スキーマ、CMSまたはAPI） |
| **状態と検証** | ライブラリコンポーネントに関連付け | API/フックを介して公開。任意のUIがそれにバインドできます |
| **チャネル** | 通常はweb （1つのフレームワーク） | 同じフォーム定義を使用して、web、モバイル、チャットなどを促進できます。 |

AEM ヘッドレスアダプティブ Formsを使用すると、AEMで[&#x200B; フォームを作成して公開できます](create-and-publish-a-headless-form.md)。任意のクライアント（React、Angular、ネイティブモバイル、チャットボット）は[&#x200B; フォーム JSON](architecture.md)を取得し、そのチャネルに適したUIでレンダリングできます。

### UI ベースのフォームソリューションの代わりにヘッドレスフォームを使用する必要があるのはなぜですか？

ヘッドレスフォームは、次のような場面で利用できます。

* **システムの一貫性を設計** - ライブラリの既定値と戦うことなく、既存のコンポーネントとブランドを使用します。
* **マルチチャネル** - web、モバイル、その他のタッチポイント用の1つのフォーム定義（[概要](overview.md)を参照）。
* **CMSまたはバックエンド駆動型のフォーム** – 作成者は、コードをデプロイせずにフォーム構造とルールを変更します。アプリはJSONを使用します。
* **フレームワークの柔軟性** - [AF-core](https://www.npmjs.com/package/@aemforms/af-core) ライブラリはフレームワークに依存しません。React バインディングは利便性のために提供されていますが、他のフレームワーク用にバインディングを構築することもできます。
* **バックエンド機能** – 特定のUI スタックにロックすることなく、事前入力、検証、送信、ワークフロー、Forms データモデルにAEM Formsを活用します。

### ヘッドレスアプローチを採用すべき理由とは？

ヘッドレスフォームは、次のような場合に使用します。

* 強力なデザインシステムやコンポーネントライブラリが必要な場合。
* Formsは、開発者以外のユーザー（CMSなど）が作成するもので、複数のアプリやチャネルをまたいで動作する必要があります。
* webやモバイルなどのクライアントでも同じフォームロジック（検証、ルール）が必要です。
* リレンダリングを最小限に抑え、UIから独立してフォームロジックをテスト可能にする必要があります。

次のような場合に、従来のUIを含むフォームライブラリを検討します。

* 単一のweb アプリで作業フォームをすばやく作成する必要があり、カスタム UIやマルチチャネルは気にする必要はありません。
* 単一のフレームワークで、コードのみでフォームを定義することを推奨しています。

### 「ヘッドレス」は単なる流行語なのか、それとも実際の問題を解決するのか？

それは実際の建築上の問題を解決します：

* **関心の分離** - フォーム構造、ルール、検証は、データとロジック レイヤーに存在します。UI レイヤーは、ユーザーのアクションのみをレンダリングおよびディスパッチします。 これにより、テストの安定性と再利用を向上できます。
* **チャネルの独立性** - 1つのフォーム定義で異なるUI （React web、React Native、Angular、音声など）を操作できます。 AEM ヘッドレスアダプティブFormsは、次の目的のために構築されています：[React、SPA、web、モバイルなど、様々な目的で一度構築すれば](overview.md)。
* **コードを使用しないオーサリング** - ビジネスユーザーは、[&#x200B; アダプティブフォームエディター](create-a-headless-adaptive-form.md)でフィールドとルールを変更できます。開発者は、コンテンツの変更のために再デプロイする必要はありません。
* **既存のスタックとの統合** - デザインシステム、状態管理、ルーティングを維持します。ヘッドレスレイヤーでは、フォームの状態、検証、送信のみを処理します。

## 導入と技術的な質問 {#implementation-technical}

### ヘッドレスフォームはどのようにステートを管理するのですか？

AEM ヘッドレスアダプティブFormsでは、ステートは&#x200B;**Forms Web SDK**&#x200B;によって管理されます。

* **ビジネス ルール プロセッサ** - フォーム JSONを受け入れ、フィールドの状態を管理し、JSONで定義されたルールとイベント ハンドラーを実行します。
* **React バインダー** - React コンポーネントが現在の状態とハンドラーを受け取るように、コントローラーにフック（`useRuleEngine`など）を提供します。同じ状態は、コア APIを介してReact以外のUIで使用できます。
* **状態**&#x200B;には、フィールド値、可視性、有効性、およびフォームモデルで定義されているすべてのカスタムプロパティが含まれます。

UI コンポーネントは、状態とハンドラー（例：`[state, handlers] = useRuleEngine(props)`）を受け取ります。ユーザーが操作を行うと、`state`からレンダリングして`handlers`を呼び出します。 ランタイムは、フォームの定義とルールに合わせて状態を維持します。 [&#x200B; アーキテクチャ &#x200B;](architecture.md)および[&#x200B; カスタムコンポーネントを使用してヘッドレスフォームをレンダリング &#x200B;](developing-for-headless-forms-using-your-own-components.md)するを参照してください。

### ヘッドレスフォーム設定での検証の仕組み

検証は、フォームロジックレイヤーの一部です。

* **制約**&#x200B;は、JSON形式（必須、最小/最大、パターンなど）で定義されます。 Forms Web SDKでは、これらの制約を適用し、検証ステート（有効/無効、エラーメッセージなど）をコンポーネントに公開します。
* **クライアント側の検証**&#x200B;は、フォーム構造に基づいてSDKによって適用されます。UIには、状態からエラーが表示されます。
* **サーバーサイド検証**&#x200B;は、AEM APIを介して利用できます（エンドポイントの検証など）。送信前または送信中に検証できます。

UIに検証ロジックを実装しません。ランタイムによって提供される検証状態とメッセージのみを表示します。

### ヘッドレスフォームをスキーマ検証（Yup、Zod、Joi）と統合できますか？

組み込みの検証は、フォーム JSON制約によって実行されます。 Yup、Zod、Joiなどを使用するには：

* スキーマからヘッドレスアダプティブフォーム JSONを&#x200B;**派生または生成**&#x200B;して（例：JSON スキーマをフォーム JSONに変換して）、信頼できる唯一の情報源がスキーマの検証とフォーム構造の両方を促進できるようにします。
* フォーム JSON以外の&#x200B;**カスタム検証**&#x200B;では、イベントハンドラーまたは送信前に独自の検証ツール（Yup/Zod/Joi）を実行し、結果をフォームの状態またはブロック送信にプッシュできます。 統合ポイントは、状態と送信に使用するフック/APIと同じです。

[&#x200B; アダプティブ Forms仕様](/help/assets/headless-adaptive-forms-specification.pdf)と[JSON式](architecture.md)は、ランタイムで使用されるルールと制約モデルを定義します。

### 非同期検証（ユーザー名の可用性など）を処理するにはどうすればよいですか？

非同期検証は、次のアプリケーションレイヤーに実装できます。

* フィールドが変更されたときにロジックをトリガーするには、JSON （サポートされている場合）フォームで&#x200B;**ルールまたはイベントハンドラー**&#x200B;を使用します。
* **カスタムコンポーネント**&#x200B;では、同じステート/ハンドラーフックを使用してバックエンド（ユーザー名可用性APIなど）を呼び出し、フィールドの有効性を更新するか、UIで表示するランタイム APIまたはローカル状態を介してエラーを表示します。
* または、ぼかし時または送信する前に&#x200B;**チェックを実行し、非同期チェックに失敗した場合は、カスタムメッセージでフィールドの状態を「無効」に設定します。**

正確なパターンは、アプリが[&#x200B; ビジネスルールプロセッサー](architecture.md)およびカスタムコンポーネントとどのように統合されるかによって異なります。

### ヘッドレスフォームを使用してAPIにデータを送信するにはどうすればよいですか？

送信はUIから切り離されます。

* **AEM送信アクション** - AEMでフォームを設定して、REST エンドポイント、メール、または統合（Microsoft Dynamics、Salesforceなど）に送信します。 フォームは、実際のHTTP/バックエンド呼び出しを処理するAEMを通じて送信されます。 [&#x200B; イベントを使用してフォームデータを処理および送信する](use-events-to-handle-and-submit-form-data.md)を参照してください。
* **クライアントサイドの送信** - アプリは、送信をリッスンしたり、ランタイム状態からフォームデータを収集したり、独自のAPIに送信したりできます。 [HTTP API](https://opensource.adobe.com/aem-forms-af-runtime/api/)のドキュメントリスト、取得、検証、送信、送信状態の追跡。
* **事前入力** - データはREST エンドポイントまたはサーバーサイドを介して事前入力できるため、フォームが読み込まれると、状態が既に入力されます。 [&#x200B; ストーリーブック – 事前入力の例](https://opensource.adobe.com/aem-forms-af-runtime/storybook/?path=/story/reference-examples--prefill-form-with-personalised-data)を参照してください。

## UIとデザイン制御 {#ui-design-control}

### ヘッドレスフォームで独自のデザインシステムやコンポーネントライブラリを使用できますか？

はい。 これがヘッドレスフォームの主な利点です。 AEM ヘッドレスアダプティブFormsの場合：

* 独自のコンポーネントを&#x200B;**マップ**&#x200B;して、フォームモデル（フィールドタイプまたはリソースタイプ別）にマッピングします。 [&#x200B; カスタムコンポーネントを使用してヘッドレスフォームをレンダリング &#x200B;](developing-for-headless-forms-using-your-own-components.md)および[Google Material UI React コンポーネントを使用してヘッドレスフォームをレンダリング &#x200B;](use-google-material-ui-react-components-to-render-a-headless-form.md)を参照してください。
* ランタイムは&#x200B;**状態とハンドラー**&#x200B;を提供します。コンポーネントはデザインシステムを使用してレンダリングされ、ハンドラーを呼び出して、フォームロジックが同期したままになります。
* **React Spectrum**、Material UI、Chakra UI、または任意のカスタムコンポーネントライブラリを使用できます。[仕様](/help/assets/headless-adaptive-forms-specification.pdf)は、カスタムコンポーネント（Chakra UI、Vue.jsなど）用に拡張できます。 [FAQ - カスタムフレームワーク &#x200B;](faq.md#is-it-possible-to-use-headless-adaptive-forms-with-custom-frameworks)を参照してください。

### ヘッドレスフォームはアクセシビリティサポート（ARIA、キーボード処理）を提供しますか？

アクセシビリティは、指定した&#x200B;**UI レイヤー**&#x200B;に実装されています。 ヘッドレスレイヤーはDOMをレンダリングしないため、ARIAやキーボードの動作を追加することはありません。 アクセシビリティ：

* デザインシステムまたはライブラリから&#x200B;**アクセス可能なコンポーネント**&#x200B;を使用する（ARIAとキーボードのサポートを含む）。
* カスタムフィールドコンポーネント（ラベル、エラーメッセージ、フォーカス管理、キーボードナビゲーション）の&#x200B;**アクセシビリティのベストプラクティス**&#x200B;に従います。
* 受け取るフォームの構造と状態（必須、無効、表示など）がコンポーネントのARIA属性と動作に反映されるようにします。

すぐに使えるReact Spectrum ベースのコンポーネントを使用すれば、組み込みのアクセシビリティがメリットになります。

### 複雑なUI コンポーネント（日付選択、カスタムドロップダウン）を処理するにはどうすればよいですか？

対応するフィールドタイプまたはカスタムリソースタイプにマッピングされた&#x200B;**カスタムコンポーネント**&#x200B;として、フォーム JSONで扱います。

* コンポーネントを実装して、他のフィールドコンポーネントと同じ&#x200B;**props/state/handlers**&#x200B;を受け入れます（例：`useRuleEngine`経由）。
* 値、表示、および有効性には&#x200B;**state**&#x200B;を使用します。値とトリガーの検証を更新するには、**ハンドラー**&#x200B;を使用します。
* 選択したUI ライブラリで日付選択またはカスタムドロップダウンをレンダリングします。変更の際には、フォームの状態が正しいままになるように、新しい値でハンドラーを呼び出します。

フィールドタイプとリソースタイプ別のマッピングについては、[&#x200B; カスタムコンポーネントを使用してヘッドレスフォームをレンダリング &#x200B;](developing-for-headless-forms-using-your-own-components.md)するを参照してください。

### フィールド（ダイナミックフォーム）を動的に追加または削除できますか？

フォーム構造は、サーバーから返された&#x200B;**フォーム JSON**&#x200B;によって定義されます。 動的な動作は、次の方法で実現されます。

* **形式のJSON**&#x200B;のルール – 式に基づいて値を表示/非表示、有効/無効、または設定します。 [&#x200B; ビジネスルールプロセッサー](architecture.md)はこれらのルールを実行します。コンポーネントは`state.visible`などに反応します。
* **サーバー駆動構造** – 異なるユーザーまたはコンテキストは、異なるフォーム JSONを受け取ることができます（例：異なるステップまたはセクション）。そのため、「動的」とは、「リクエストごとに異なるフォーム定義」を意味します。
* **クライアントサイドの変更** - アプリがフォームモデルを変更できる場合（繰り返し可能な構造の項目の追加や削除など）、ランタイムはそれを反映できます。正確な機能は、フォームスキーマとランタイム APIによって異なります。

[&#x200B; ストーリーブック &#x200B;](https://opensource.adobe.com/aem-forms-af-runtime/storybook/)には、動的な動作の例が含まれています。

### コンディショナルフィールド（入力に基づいて表示/非表示）を処理するにはどうすればよいですか？

条件付き表示は、ビジネスルールプロセッサーによって評価されるJSON フォームの&#x200B;**ルール**&#x200B;によって駆動されます。 条件を定義します（例：「フィールド AがXに等しい場合、フィールド Bを表示」）。ランタイムの更新状態（例：`state.visible`）。 コンポーネントは、**状態**&#x200B;を尊重する必要があります（例：`if (!state.visible) return null;`）。 状態からのレンダリング以外に、表示/非表示に追加のUI ロジックは必要ありません。 カスケーディングと条件付きの動作は、[&#x200B; アダプティブ Formsの仕様](/help/assets/headless-adaptive-forms-specification.pdf)で文書化され、[&#x200B; ストーリーブック – カスケーディングフィールド &#x200B;](https://opensource.adobe.com/aem-forms-af-runtime/storybook/?path=/story/adaptive-form-dynamic-behaviour--options&args=formJson.items[0].fieldType:drop-down;formJson.items[0].minimum:!undefined;formJson.items[0].maximum:!undefined;formJson.items[0].label.value:Choose+number+of+options;formJson.items[0].enum[0]:1;formJson.items[0].enum[1]:2;formJson.items[0].enum[2]:3;formJson.items[1].fieldType:drop-down)で説明されています。 [FAQ - カスケーディングフィールド &#x200B;](faq.md#do-headless-adaptive-forms-support-cascading-fields)も参照してください。

## パフォーマンスおよびスケーラビリティ {#performance-scalability}

### ヘッドレスフォームは、従来のフォームライブラリよりもパフォーマンスが高いですか？

可能ですが、実装によって異なります。

* **ターゲット設定された更新** – 適切に設計されたヘッドレスランタイムは、変更された状態のみを更新し、それに依存するコンポーネントのみを通知します。これにより、モノリシックフォームコンポーネントと比較して不要な再レンダリングを減らすことができます。
* **より小さいUI バンドル** - ライブラリ コンポーネントの完全なセットではなく、使用するUI コンポーネント（デザイン システム）のみを出荷します。
* **遅延読み込み** – 必要に応じてフォーム JSONを取得できます。初期バンドルは小さくできます。

パフォーマンスは、コンポーネントの実装方法（不要な再レンダリングの回避、メモ化など）にも依存します。

### リレンダリングを最小限に抑えるにはどうすればよいか？

* **状態シェイプ** - ランタイムは、細かく調整された更新を可能にする構造でフォームの状態を保持するため、ツリーの影響を受ける部分のみが再レンダリングする必要があります。
* **フックデザイン** - `useRuleEngine`のようなフックを実装して、使用する状態にのみコンポーネントをサブスクライブできます。そのため、親または兄弟の変更によって、すべてのフィールドが再レンダリングされるわけではありません。
* **お客様の責任** - カスタムコンポーネントでReactのベストプラクティス（`React.memo`、安定したコールバックなど）を使用することで、再レンダリングをさらに最小限に抑えることができます。

### ヘッドレスフォームは、大規模なマルチステップのフォームに対応していますか？

はい、適切に設計されている場合：

* **フォーム定義** – 大きなフォームはJSON内のステップまたはセクションに分割できます。表示されるステップ/セクションのみがUIで完全にアクティブになる必要があり、サポートされている場合は非表示セクションのルールを遅延評価する必要があります。
* **状態** - ランタイムは、一貫したフォーム状態を1つ保持します。ステップナビゲーションは、データを複製することなく、セクションを表示/非表示にしたり、「現在のステップ」を更新したりするだけです。
* **チャンク化と遅延読み込み** - フォーム JSONをチャンクで取得するか、手順を事前に追加のセクションを読み込むことで、初期ペイロードと解析コストを低く抑えることができます。

非常に大きなフォームの場合は、構造（ウィザードの手順など）、サーバー駆動型フォームのバリエーション、実際のペイロードを使用したレンダリングとルールの実行の測定を検討します。

## 統合とエコシステム {#integration-ecosystem}

### ヘッドレスフォームは、Next.js/SSR/サーバーアクションで動作しますか？

* **Next.js / React** – はい。 React レンダラーとフックはReact環境で動作します。 クライアントコンポーネントでForms Web SDKを使用します。必要に応じて、サーバーまたはクライアントでフォーム JSONを取得します。
* **SSR** - フォーム JSONをサーバー上で取得し、それをクライアントに渡すことで、フォームがデータと共にハイドレートされます。 フォームのインタラクティブ機能（ステート、検証、ルール）は、SDKが読み込まれるクライアント上で実行されます。 SSR中にクライアントのみの状態に依存するフォームフィールドのレンダリングを避けるか、クライアントでハイドレートするプレースホルダーを使用します。
* **サーバーアクション（Next.js）** - サーバーアクションは、送信ハンドラーから呼び出すことができます。ユーザーが送信すると、クライアントコードは（ヘッドレス状態から）フォームデータを収集し、AEM送信エンドポイントの代わりまたは追加のサーバーアクションを呼び出します。

### ヘッドレスフォームは、CMS、ヘッドレスコマース、バックエンドシステムとどのように統合できますか？

* **CMS** - AEMは、フォーム定義のCMSです。作成者は、フォーム JSONを作成して公開します。 他のCMSでは、フォームのURLやAPIを参照したり、リンクしたりできます。 アプリはAEM（またはCDN）からフォームを取得し、オプションで別のCMSからコピーまたはレイアウトを取得します。
* **事前入力と送信** - [事前入力](https://opensource.adobe.com/aem-forms-af-runtime/storybook/?path=/story/reference-examples--prefill-form-with-personalised-data)と送信はREST エンドポイントにヒットする可能性があるため、CRM、DAM、コマースのバックエンドから事前入力を行い、同じシステムまたは異なるシステムに送信することができます。 AEM Formsでは、[Microsoft DynamicsおよびSalesforce](faq.md)、REST、電子メール、カスタム送信アクションもサポートしています。
* **Forms Data Model** - AEM Formsは、様々なデータソースに接続するためのForms データモデルを提供します。ヘッドレスフォームは、すべての統合を自分で構築することなく、これらの機能を事前入力、検証、送信に使用できます。

モバイルおよびオフラインのシナリオの場合、推奨されるアプローチは、[独自のアプリを構築し、ヘッドレスアダプティブForms API](mobile-forms-best-practices.md)を使用してフォーム定義を取得することです。
